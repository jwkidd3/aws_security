Shared Responsibility Matrix

Module 1 — Security on AWS

🎯 Objective

Gather real evidence in the AWS console of where the Shared Responsibility line sits for three services — S3, Lambda, and EC2 — then use that evidence to fill in a responsibility matrix for three realistic workloads.

  • Part 1 — S3: what AWS turns on for you, and what stays yours
  • Part 2 — Lambda: who patches the runtime, who owns the permissions
  • Part 3 — EC2: walk the launch wizard (no launch) and count your decisions
  • Part 4 — Fill in the matrix for three workloads

👥 Shared class account: everyone works in the same AWS account. Start every resource name with your student ID, and only open, change, or delete resources that start with your ID.

📚 Terms You'll See

  • Shared Responsibility Model — AWS secures the cloud; you secure what's in it
  • IaaS / PaaS / SaaS — layers of abstraction; the line shifts as you climb
  • EC2 — virtual server (IaaS) — you own the OS
  • RDS — managed database — AWS owns the engine, you own schema & access
  • S3 — object storage — AWS runs it, you own access & data choices
  • Lambda — run code without servers; AWS patches the runtime
  • KMS — AWS encryption-key service; you choose AWS managed vs. customer managed keys
  • SSE-S3 — server-side encryption with keys S3 manages for you
  • Block Public Access (BPA) — S3 guardrail that overrides public ACLs and policies
  • Execution role — the IAM role a Lambda function assumes when it runs
  • IMDSv2 — token-based EC2 instance metadata service (hardened against SSRF)

📦 Part 1 — Create an S3 Bucket

  1. Open S3 → Buckets → Create bucket
  2. Bucket type: General purpose · Bucket namespace: keep Global namespace
  3. Bucket name: <student-id>-lab1-<account-id> (e.g. stu07-lab1-123456789012)
  4. Leave every other setting at its default — do not touch encryption or Block Public Access
  5. Choose Create bucket
  6. Open the new bucket → Upload → Add files → pick any small text file → Upload

✅ Check: the bucket appears in the list and the object shows in the Objects tab.

🔍 Part 1 — What Did AWS Turn On for You?

  1. Bucket → Properties tab → Default encryption panel
  2. Click your uploaded object → Properties → Server-side encryption settings
  3. Bucket → Permissions tab → Block public access (bucket settings)
  4. Same tab → Object Ownership

✅ Check:

  • Default encryption: Server-side encryption with Amazon S3 managed keys (SSE-S3) — and the object is encrypted with it
  • Block all public access: On (all four settings)
  • Object Ownership: Bucket owner enforced (ACLs disabled)

🚫 Part 1 — Try to Make It Public

  1. Permissions tab → Bucket policy → Edit
  2. Paste the policy below, replacing the bucket name with yours
  3. Choose Save changes

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::<student-id>-lab1-<account-id>/*"
  }]
}

✅ Check: the save fails with an access-denied error saying the public policy conflicts with Block Public Access. Choose Cancel.

🧾 Part 1 — Record Your Evidence

  • Encrypting the disks and the data at rest — AWS does it by default (SSE-S3)
  • Choosing a different key (SSE-KMS, your own KMS key) — Customer
  • Safe defaults (BPA on, ACLs off) — AWS sets them…
  • …but you can turn BPA off and write any bucket policy — access is Customer

Every "S3 bucket leak" headline is a customer-side configuration change that overrode these defaults.

⚡ Part 2 — Create a Lambda Function

  1. Open Lambda → Functions → Create function
  2. Choose Author from scratch
  3. Function name: <student-id>-lab1-fn
  4. Runtime: change the default (Node.js) to the newest Python 3.x in the list
  5. Leave Additional settings as is — ARM64 architecture and Custom execution role stay off, so you get x86_64 and a new role with basic Lambda permissions
  6. Choose Create function

✅ Check: a green banner confirms the function was created, and the Code tab shows a lambda_function.py that returns 'Hello from Lambda!'.

▶️ Part 2 — Run It and Inspect the Runtime

  1. Test tab → Create new event · Event name lab1-test · Template Hello World → Save
  2. Choose Test to invoke the function
  3. On the Code tab, scroll to Runtime settings
  4. Choose Edit runtime management configuration — read it, then Cancel

✅ Check:

  • Execution result Succeeded; response {"statusCode": 200, "body": "\"Hello from Lambda!\""}
  • Runtime update mode is Auto — AWS rolls new runtime and OS patches onto your function automatically

🔐 Part 2 — Who Owns the Permissions and Logs?

  1. Configuration tab → Permissions → note the Execution role name (<student-id>-lab1-fn-role-xxxxxxxx)
  2. Click the role name — it opens in IAM. Expand its policy: it only allows CloudWatch Logs actions
  3. Back in Lambda: Monitor tab → View CloudWatch logs
  4. In CloudWatch, open Log groups and find /aws/lambda/<student-id>-lab1-fn — note the Retention column

✅ Check: retention shows Never expire. Nobody at AWS will set that for you.

Evidence: runtime patching = AWS · code, execution role, log retention = Customer

🖥️ Part 3 — Walk the EC2 Launch Wizard (No Launch!)

You will not launch an instance. You are counting the security decisions EC2 hands to you.

  1. Open EC2 → Instances → Launch instances
  2. Name: <student-id>-lab1-wizard
  3. Application and OS Images: note the default Amazon Linux 2023 AMI — that guest OS is yours to patch
  4. Key pair (login): open the drop-down — note you would create and protect the SSH key. Do not create one
  5. Network settings: Network shows –; choose Edit — VPC - required has nothing preselected because there is no default VPC (AWS normally creates one in every Region; the class account's was removed). Note the proposed launch-wizard security group allows SSH from Anywhere (0.0.0.0/0) by default

✅ Check: no VPC is preselected (any VPCs in the list were built by classmates, not AWS), and the default SSH-from-anywhere rule is yours to tighten — networking is a customer build.

🖥️ Part 3 — Storage, Metadata, then Cancel

  1. Configure storage → Advanced → expand the root volume and look at Encrypted
  2. Advanced details → scroll to Metadata version
  3. In the Summary panel choose Cancel — do not choose Launch instance
  4. Optional: open VPC → Your VPCs in us-east-1 and confirm no VPC shows Default VPC: Yes

✅ Check:

  • Root volume Encrypted: Not encrypted (unless your account enabled EBS encryption by default) — your choice
  • Metadata version: V2 only (token required) — the AL2023 AMI defaults to IMDSv2, but you can change it
  • No instance was created — searching Instances for <student-id>-lab1 returns nothing

🔗 Answer Key — What "Shared" Means

  • AWS — physical DC, hypervisor, network fabric, storage media, managed-service engine patching (RDS, Lambda runtime, DynamoDB), edge TLS infrastructure
  • Customer — guest OS, app code & config, IAM policies, SG rules, bucket/key policies, log retention, app users, TLS certs you own, responding to findings
  • Shared — patching (AWS patches infra, you patch guest OS), configuration management, incident response (AWS detects infra events, you handle workload events), awareness & training
