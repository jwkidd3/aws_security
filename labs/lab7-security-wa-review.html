Module 6 — Course Wrap-Up

🎯 Objective

Run a real Security Pillar review of a fictional workload in the AWS Well-Architected Tool:

  • Define the workload and answer five key Security questions honestly
  • Read the High / Medium risk summary and the Improvement plan
  • Save a baseline milestone
  • Score the seven design principles and build a Top-3 roadmap
  • Re-answer as if the top three shipped, and compare milestones

👥 Shared class account: everyone works in the same AWS account. Start every resource name with your student ID, and only open, change, or delete resources that start with your ID.

📚 Terms You'll See

  • Well-Architected Review — structured walkthrough of a workload against AWS best practices
  • Workload — the collection of resources delivering business value
  • Lens — a set of questions; the AWS Well-Architected Framework lens has 57 questions across six pillars (11 in Security)
  • Best practice (choice) — a checkbox under a question; tick only what is true today
  • Risk — High / Medium / None, calculated from which best practices are not ticked
  • Improvement plan — the tool's list of risky questions, linked to the best-practice guidance
  • Milestone — a saved, read-only snapshot of the review; compare milestones to show progress

🛒 Scenario — "OrderFlow"

A 2-year-old e-commerce order-processing workload in one AWS account:

  • Runs in one region, one VPC, one account shared with two other apps
  • Public ALB → EC2 auto-scaling group → RDS MySQL (Multi-AZ)
  • Images & receipts in S3 (orderflow-assets, public-read for CloudFront)
  • Developers use IAM users with access keys; keys last rotated "a while ago"; no MFA evidence
  • CloudTrail enabled in us-east-1 only; logs go to the same account
  • GuardDuty is "on the roadmap"; no Config rules
  • Secrets are in a .env file baked into the AMI
  • TLS on the ALB with an ACM certificate; RDS doesn't enforce SSL; S3 bucket has default SSE-S3
  • No documented IR process; no game days ever run

🏗️ Part 1 — Define the Workload

  1. Open AWS Well-Architected Tool → Workloads → Define workload (in its menu, choose Define workload — not Define from review template)
  2. Name: <student-id>-OrderFlow
  3. Description: E-commerce order-processing workload (lab scenario)
  4. Review owner: your name (at least 3 characters)
  5. Environment: Production
  6. Regions: tick AWS Regions and choose US East (N. Virginia)

Required fields: name, description, review owner, environment, at least one region, and a lens. Leave one out and the tool refuses to create the workload.

✅ Sample Answer — Scoring

  • Identity — Gap: IAM users + long-lived keys; no Identity Center; no MFA evidence (SEC 2 High)
  • Traceability — Gap: CloudTrail single-region, no central log account, GuardDuty off (SEC 4 Medium — logging exists, little else)
  • Layers — Partial: VPC + SGs exist, but S3 bucket public-read, no WAF
  • Automate — Gap: no Config rules, no SCPs, no policy-as-code
  • Protect data — Partial: ALB TLS yes; RDS no SSL enforcement; SSE-S3 but no customer managed key for sensitive data (SEC 8, SEC 9 High)
  • Keep people away — Gap: secrets in .env baked into AMI; devs have direct creds
  • Prepare for events — Gap: no IR plan, no game days, no break-glass roles (SEC 10 High)

🏆 Sample Answer — Roadmap

  1. Multi-region CloudTrail to a log-archive account + GuardDuty, High findings routed by EventBridge to the ticket queue (SEC 4) — visibility is the prerequisite for everything else
  2. Move developers to IAM Identity Center with MFA; delete IAM user access keys (SEC 2)
  3. Move secrets out of the AMI into Secrets Manager with automatic rotation (SEC 2)
  4. Enforce TLS to RDS (require_secure_transport in the DB parameter group) (SEC 9)
  5. Fix the public orderflow-assets bucket — CloudFront with OAC + Block Public Access on; KMS key for receipts (SEC 8)

#1–#3 are the sample Top-3; #4–#5 are next in line. WAF, Config rules, and an IR plan (SEC 10) still matter — these give the most risk reduction for the least effort, and most unlock the rest.

🔁 Task 3 — Re-Score in the Tool

Assume the sample top three (CloudTrail + GuardDuty, Identity Center, Secrets Manager) have shipped. Continue reviewing → Security:

  1. SEC 4 — keep Configure service and application logging; add Capture logs, findings, and metrics in standardized locations and Correlate and enrich security events
  2. SEC 2 — untick None of these; tick Use strong sign-in mechanisms, Use temporary credentials, Store and use secrets securely, Rely on a centralized identity provider, Audit and rotate credentials periodically
  3. Save and exit → Save milestone → name after-top-3 → Save
  4. Open the Milestones tab and compare the two milestones' risk counts

✅ Check: baseline = 4 High / 1 Medium; after-top-3 = 3 High / 2 Medium (SEC 2 now Medium, SEC 4 still Medium).

🗝️ Answer Key — What the Re-Score Tells You

  • SEC 2 only reached Medium — Employ user groups and attributes is still unticked; ticking it too gives None
  • SEC 4 didn't move — three roadmap items shipped, still Medium: Initiate remediation for non-compliant resources (Config rules + automated remediation) is missing; with it SEC 4 is None
  • In the design principles: Traceability Gap → Partial; Identity Gap → Partial; Keep people away from data Gap → Partial
  • Didn't move at all: SEC 8, SEC 9, SEC 10 — Protect data and Prepare for events are your next round
  • Cheapest next win: enforcing TLS to RDS lets you tick Enforce encryption in transit — SEC 9 goes High → None
  • Lesson: the tool rewards complete practices, not effort — a ticket that covers half a question rarely changes its risk

⭐ Extra — If You Finish Early

  1. Report: open the lens (AWS Well-Architected Framework) → Generate report — a PDF downloads. Its "Improvement item summary" matches the workload page: High risk: 3, Medium risk: 2 after the re-score
  2. Ticket: write your #1 roadmap item as an engineering ticket — Title (starts with a verb), Risk (in business terms), Acceptance criteria (e.g., Config rule multi-region-cloudtrail-enabled is compliant), AWS services, Evidence for an auditor
  3. Sample ticket: "Enable organization-wide CloudTrail delivered to a log-archive account, with GuardDuty alerting" — multi-region trail with log-file validation, S3 Object Lock, Config rule compliant, GuardDuty High findings routed by EventBridge to a ticket
  4. Evidence: open Trusted Advisor → Security (read-only — change nothing) and note which SEC question each check backs up (e.g., root MFA → SEC 1 / SEC 2; unrestricted ports → SEC 5)

On a real review, attach that evidence in each question's Notes box so the next reviewer can verify your answer.
