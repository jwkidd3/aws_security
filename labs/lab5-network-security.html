Network Security Design

Module 4 — Security IN the Cloud · Part 2

🎯 Objective

Build a real VPC for a 3-tier web app in the AWS console, wire up a security-group reference graph, review a flawed configuration, lock down an S3 gateway endpoint with an endpoint policy, and add a NACL deny rule — then decide which network control fits which job.

You will not launch instances, databases, load balancers, or NAT gateways. Everything you build here is free and is deleted at the end.

👥 Shared class account: everyone works in the same AWS account. Start every resource name with your student ID, and only open, change, or delete resources that start with your ID.

📚 Terms You'll See

  • VPC — your isolated virtual network in AWS
  • Subnet — slice of the VPC's IP range tied to one AZ
  • IGW (Internet Gateway) — route target that makes a subnet public
  • NAT Gateway — egress-only internet for private subnets
  • Route table — rules that decide where a subnet's traffic goes
  • Prefix list — named set of CIDRs; AWS publishes one for S3 per region
  • Security group — stateful firewall on an ENI; default-deny inbound, allow rules only
  • NACL — stateless subnet firewall; numbered allow and deny rules
  • VPC endpoint — private path from your VPC to AWS services (Gateway or Interface)
  • Endpoint policy — resource policy on a VPC endpoint limiting what can pass through it
  • ALB — Application Load Balancer (L7)

🏗️ Scenario — 3-Tier Web App

  • Public ALB terminates HTTPS
  • App tier: auto-scaling EC2 in private subnets, one region, two AZs
  • Data tier: RDS PostgreSQL, Multi-AZ, no public endpoint
  • App needs to reach S3 and Secrets Manager
  • Engineers connect via SSM Session Manager — no SSH keys

You will build the network for this app. The compute and database are described, not launched.

✅ Task 2 — Sample Answer

  • sg-alb — inbound 443 from 0.0.0.0/0 (and 80 if you redirect to 443)
  • sg-app — inbound 8080 from sg-alb
  • sg-db — inbound 5432 from sg-app
  • sg-vpce — inbound 443 from sg-app

SG-to-SG references make the "app may reach DB" relationship explicit and survive IP changes: any ENI that carries sg-app is allowed, no matter which subnet or IP it lands on.

Outbound: tightening it (e.g., sg-app egress only to sg-db:5432, sg-vpce:443, and the S3 prefix list) limits what a compromised instance can reach.

🔐 Task 4 — Lock Down the S3 Endpoint

Your gateway endpoint was created with the Full access policy ("Action": "*" on "Resource": "*"), so a compromised app instance could copy data to any bucket in the world — including an attacker's.

  1. Write an endpoint policy that allows only s3:GetObject and s3:PutObject on the company buckets <student-id>-orders-* in your account
  2. Which condition key would restrict access to buckets owned by any account in your organization, without listing every bucket?
  3. Why does the endpoint policy not replace the app's IAM role policy?

Hint: an endpoint policy uses IAM policy syntax but also needs a Principal. Find your 12-digit account ID in the account menu (top right).

🛠️ Task 4 — Apply the Endpoint Policy

  1. VPC → PrivateLink and Lattice → Endpoints
  2. Select <student-id>-lab5-vpce-s3 (Type Gateway, Status Available)
  3. Policy tab — note the current full-access JSON
  4. Actions → Manage policy → choose Custom
  5. Replace the JSON with the policy on the next slide, replacing STUDENT-ID and ACCOUNT-ID
  6. Save

✅ Check: the Policy tab now shows your CompanyBucketsOnly statement, and the endpoint is still Available. Private route tables are unchanged — the policy filters traffic; the route still sends it.

📝 Task 4 — Policy to Paste

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CompanyBucketsOnly",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::STUDENT-ID-orders-*/*",
      "Condition": {
        "StringEquals": { "aws:ResourceAccount": "ACCOUNT-ID" }
      }
    }
  ]
}

Try it: delete the "Principal" line and save — the save is rejected as an invalid VPC endpoint policy. Put it back and save again.

Caution: a misspelled action (e.g. s3:GetObjectt) is accepted without error — it just never matches. Endpoint policies fail closed, so typos break your app silently.

✅ Task 4 — Sample Answer

  • Policy: as on the previous slide. Resource limits bucket names; aws:ResourceAccount blocks a look-alike bucket named <student-id>-orders-x that an attacker creates in their account
  • Org-wide: aws:ResourceOrgID (bucket owned by any account in your AWS Organization) — no bucket list to maintain
  • Not a replacement: the IAM policy, the endpoint policy, and the bucket policy must all allow the request. The endpoint policy is a data-exfiltration guardrail, not a substitute for least privilege
  • Real-world gotcha: instances also pull from AWS-owned buckets (e.g., Amazon Linux package repos, SSM agent updates) — production policies add statements for those

🧱 Task 5 — When Would You Touch a NACL?

Security groups handle almost everything. For each situation, decide: Security group, NACL, or WAF, and give a one-line reason.

SituationControlWhy
Block a known-bad IP range from reaching anything in the public subnets, immediately
Allow only the app tier to reach the database
Block SQL-injection attempts against the login page
Make sure the isolated DB subnets can never talk to the public subnets, even if someone misconfigures an SG
Rate-limit a single client hammering the search API

Then build the first one: block 203.0.113.0/24 on the public subnets.

🛠️ Task 5 — Create a Public-Subnet NACL

  1. VPC → Security → Network ACLs → Create network ACL
  2. Name <student-id>-lab5-public-nacl, VPC: your lab VPC → Create network ACL
  3. Select it → Inbound rules tab: only * All traffic Deny — a new NACL denies everything
  4. Edit inbound rules → Add new rule: Rule number 90, Type All traffic, Source 203.0.113.0/24, Deny

You use a custom NACL rather than editing the default one, because the default NACL also covers your private subnets.

✅ Task 5 — Sample Answer

  • Bad IP range — NACL (or WAF IP set for HTTP traffic): SGs have no deny rules; NACLs do
  • App → DB — Security group: SG-to-SG reference from sg-app
  • SQL injection — WAF: it's L7; SGs and NACLs only see ports and IPs
  • Subnet isolation backstop — NACL: a subnet-level deny that holds even when an SG is wrong (defense in depth)
  • Rate limiting — WAF rate-based rule

NACLs are stateless — your outbound allow-all rule is what lets return traffic (ephemeral ports 1024–65535) leave. A tight outbound NACL that forgets those ports breaks connections.
