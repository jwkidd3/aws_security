Data Protection & KMS

Module 3 — Security IN the Cloud · Part 1

🎯 Objective

Protect a fictional healthcare workload's data in the shared class account:

  • Create a customer managed KMS key and read its key policy
  • Build an S3 bucket that encrypts with that key by default
  • Apply a bucket policy that rejects the wrong encryption and non-TLS requests — then prove it from CloudShell
  • Disable the key and see what breaks

Finish early? An Extra slide adds key rotation, TLS for PostgreSQL, and a Secrets Manager secret.

👥 Shared class account: everyone works in the same AWS account. Start every resource name with your student ID, and only open, change, or delete resources that start with your ID.

📚 Terms You'll See

  • KMS key — logical key in AWS Key Management Service (KMS); you grant use of it via a key policy
  • AWS managed key — AWS creates it per service (e.g. aws/s3); simple, no monthly fee, you can't edit its policy
  • Customer managed key — you own the key policy, rotation, grants, and audit trail
  • Envelope encryption — KMS encrypts a per-object data key; the data key encrypts the data
  • Key policy — resource policy attached to a KMS key (required, not optional)
  • S3 Bucket Key — a bucket-level data key that cuts KMS calls (and cost) for SSE-KMS
  • SSE-S3 / SSE-KMS — S3 encryption with S3-managed keys vs. with a KMS key
  • CloudShell — browser-based terminal in the console, already signed in as you

🏥 Scenario — "HealthMetric" Workload

A regulated healthcare analytics workload running in one AWS account.

  • S3 bucket holding raw patient data exports (PHI)
  • RDS PostgreSQL holding reporting data (derived, pseudonymized)
  • EBS volumes attached to EC2 processing nodes
  • Secrets Manager storing DB connection strings & third-party API keys
  • CloudTrail logs delivered to a separate log-archive bucket

You'll build the key and the PHI bucket. No EC2, RDS instances, or load balancers are launched.

🔑 Task 1 — Pick the Right Key

For each resource, pick AWS managed key, Customer managed key, or CloudHSM-backed key, and justify in one line.

ResourceYour choiceWhy

✅ Task 1 — Sample Answer

  • PHI S3 bucket — customer managed key: regulated data; you need a key policy that names exactly who can decrypt, plus per-key CloudTrail audit
  • EBS — AWS managed key is usually enough; turn on EBS encryption by default for the region
  • CloudTrail bucket — customer managed key: the log-archive team, not the workload team, should control decryption
  • CloudHSM-backed: none of these, unless a regulator specifically requires single-tenant key hardware

🔐 Part 1 — Create a Customer Managed Key

  1. Open Key Management Service (KMS) → Customer managed keys → Create key
  2. Key type: Symmetric · Key usage: Encrypt and decrypt → Next
  3. Alias: <student-id>-healthmetric-phi · Description: HealthMetric PHI data key → Next
  4. Key administrators: select your own user or role → Next
  5. Key users: select your own user or role → Next · Edit key policy (optional): leave as is → Next
  6. Review → Finish
  7. Open the key and copy its ARN (arn:aws:kms:us-east-1:<account-id>:key/…) to your notepad
  8. Key policy tab → Switch to policy view → note each statement's Sid and Principal
✅ Check: status Enabled; four statements — Enable IAM User Permissions (account root, kms:*), Allow access for Key Administrators, Allow use of the key, Allow attachment of persistent resources (grants only when kms:GrantIsForAWSResource is true). Every principal is inside your account.

Can't find yourself in the list? Skip that step — the root statement still lets your admin permissions manage the key (you'll see fewer statements).

📜 Task 2 — Review This Key Policy

{
  "Version": "2012-10-17",
  "Id": "phi-bucket-key",
  "Statement": [
    { "Sid": "EnableRoot", "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "kms:*", "Resource": "*" },
    { "Sid": "AllowEveryone", "Effect": "Allow",
      "Principal": "*",
      "Action": [
        "kms:Encrypt","kms:Decrypt","kms:GenerateDataKey",
        "kms:DescribeKey","kms:ReEncrypt*"
      ],
      "Resource": "*" }
  ]
}

Compare it with the policy on your key. List at least 3 problems. Which statement is dangerous, and what would you change?

🗝️ Task 2 — Answer Key

  • "Principal": "*" allows any AWS principal, including other accounts — this is the headline bug. Your key names only principals in your account.
  • No kms:ViaService condition → the key can be used from any service, not just S3
  • No kms:CallerAccount / aws:PrincipalAccount condition → no account-scope guardrail
  • Including kms:ReEncrypt* with wildcards is often broader than needed
  • Fix: restrict Principal to specific role ARNs, add "kms:ViaService": "s3.us-east-1.amazonaws.com", and scope actions to what the workload actually needs

🪣 Part 2 — Create the PHI Bucket

  1. S3 → Buckets → Create bucket · Bucket type: General purpose · namespace: Global namespace
  2. Name: <student-id>-healthmetric-phi-<account-id>
  3. Leave Block all public access on
  4. Default encryption → Encryption type: Server-side encryption with AWS Key Management Service keys (SSE-KMS)
  5. AWS KMS key: Choose from your AWS KMS keys → pick <student-id>-healthmetric-phi
  6. Bucket Key: Enable → Create bucket
✅ Check: bucket → Properties → Default encryption shows SSE-KMS, your key's ARN, and Bucket Key Enabled.

✏️ Part 3 — Apply an Encryption + TLS Bucket Policy

Bucket → Permissions → Bucket policy → Edit. Paste, replace BUCKET (4×) and KEY-ARN with yours → Save changes.

{ "Version": "2012-10-17",
  "Statement": [
    { "Sid": "DenyInsecureTransport", "Effect": "Deny", "Principal": "*", "Action": "s3:*",
      "Resource": ["arn:aws:s3:::BUCKET", "arn:aws:s3:::BUCKET/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } } },
    { "Sid": "DenyNonKmsEncryption", "Effect": "Deny", "Principal": "*",
      "Action": "s3:PutObject", "Resource": "arn:aws:s3:::BUCKET/*",
      "Condition": {
        "Null": { "s3:x-amz-server-side-encryption": "false" },
        "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" } } },
    { "Sid": "DenyWrongKmsKey", "Effect": "Deny", "Principal": "*",
      "Action": "s3:PutObject", "Resource": "arn:aws:s3:::BUCKET/*",
      "Condition": { "StringNotEqualsIfExists": {
        "s3:x-amz-server-side-encryption-aws-kms-key-id": "KEY-ARN" } } }
  ] }
✅ Check: the policy saves with no error — Deny-only statements don't conflict with Block Public Access.

🧠 Part 3 — How the Policy Works

  • DenyInsecureTransport — any request over plain HTTP is refused
  • DenyNonKmsEncryption — if the upload sends an encryption header (Null = false) and it isn't aws:kms → deny (blocks SSE-S3 and DSSE-KMS)
  • DenyWrongKmsKey — S3 fills in the key the upload will actually use (including the bucket default), so any key other than yours → deny; no KMS key at all (SSE-S3) → deny
  • Uploads that send no encryption header get the bucket default (your key) → allowed

⚠️ Common mistake: StringNotEquals (or StringNotEqualsIfExists) on s3:x-amz-server-side-encryption by itself also matches when the header is missing — it would block every upload that relies on default encryption, including ordinary console uploads.

💻 Part 4 — Test Every Request (CloudShell)

Open CloudShell (terminal icon in the console's top bar, us-east-1). Set your names, then run each command:

B=<student-id>-healthmetric-phi-<account-id>
K=alias/<student-id>-healthmetric-phi
echo "patient record" > patient-001.txt

# 1: no encryption setting (bucket default)
aws s3 cp patient-001.txt s3://$B/
# 2: SSE-S3
aws s3 cp patient-001.txt s3://$B/sse-s3.txt --sse AES256
# 3: SSE-KMS with the AWS managed aws/s3 key
aws s3 cp patient-001.txt s3://$B/wrong-key.txt --sse aws:kms --sse-kms-key-id alias/aws/s3
# 4: SSE-KMS with YOUR key
aws s3 cp patient-001.txt s3://$B/right-key.txt --sse aws:kms --sse-kms-key-id $K
# 5: list over plain HTTP, then over HTTPS
aws s3 ls s3://$B --endpoint-url http://s3.us-east-1.amazonaws.com
aws s3 ls s3://$B
✅ Check: #1 and #4 print upload: … · #2 and #3 print upload failed … AccessDenied … explicit deny in a resource-based policy · HTTP list AccessDenied … explicit deny · HTTPS list shows patient-001.txt and right-key.txt.

🔍 Part 4 — Which Key Encrypted Object #1?

aws s3api head-object --bucket $B --key patient-001.txt
✅ Check: "ServerSideEncryption": "aws:kms", "SSEKMSKeyId" = your key's ARN, "BucketKeyEnabled": true.

You never chose a key for upload #1 — the bucket default did it, and the policy allowed it. The same is true for an ordinary console upload.

🔌 Part 5 — Pull the Plug: Disable the Key

  1. KMS → Customer managed keys → select your key → Key actions → Disable → confirm
  2. Wait ~30 seconds, then in CloudShell: aws s3 cp s3://$B/patient-001.txt -
  3. Back in KMS → Key actions → Enable, wait ~30 seconds, and run the same command again
✅ Check: while disabled: download failed … KMS.DisabledException … is disabled. After re-enabling: patient record is printed.

The data never moved — only access to the key changed. That's the power (and risk) of a customer managed key.

⭐ Extra — If You Finish Early

Optional. Each item stands alone; your key must be Enabled.

  1. Key rotation: KMS → your key → Key material and rotations tab → Automatic key rotation → Edit → Enable (keep 365 days) → Save. ✅ A next rotation date one year out.
  2. TLS for PostgreSQL: Aurora and RDS → Parameter groups → Create parameter group · Name <student-id>-force-ssl · Description HealthMetric TLS settings · Engine type PostgreSQL · Family postgres16 · Type DB Parameter Group → Create
  3. Open the group, search ssl → Edit → ssl_min_protocol_version = TLSv1.3 → Save changes. ✅ rds.force_ssl is already 1 (default for PostgreSQL 15+; 0 for postgres14 and earlier). A parameter group does nothing until a DB instance uses it.
  4. Secret with your key: Secrets Manager → Store a new secret → Other type of secret · username = report_reader, password = Example-Only-123 · Encryption key: your key → Next · Name <student-id>/healthmetric/reporting-db → Next → Next (rotation off) → Store
  5. Open the secret → Retrieve secret value. Disable your key, wait ~30 s, retry → DecryptionFailure (the key "is disabled"). Re-enable the key.

🧹 Cleanup

  1. (if you did the Extra) Secrets Manager → your secret → Actions → Delete secret → waiting period 7 days → Schedule deletion
  2. (if you did the Extra) Aurora and RDS → Parameter groups → select <student-id>-force-ssl → Actions → Delete
  3. CloudShell (if it restarted, set B and K again first):
KID=$(aws kms describe-key --key-id $K --query KeyMetadata.KeyId --output text)
aws s3 rm s3://$B --recursive
aws s3 rb s3://$B
aws kms delete-alias --alias-name $K
aws kms schedule-key-deletion --key-id $KID --pending-window-in-days 7
rm patient-001.txt
✅ Check: remove_bucket: … is printed; the key shows "KeyState": "PendingDeletion" with a deletion date 7 days out; any secret shows a deletion date and the parameter group is gone.

💬 Discussion

  • When is an AWS managed key genuinely sufficient — and when is the audit burden of a customer managed key worth it?
  • Your org standard says "encrypt everything." How do you enforce that in code/pipelines rather than at review time?
    Config rules · SCPs forbidding unencrypted resources · cdk-nag / checkov in CI
  • How would you enforce TLS end to end — at the ALB, to RDS, to S3, and between services inside the VPC?
    HTTPS listener + ACM cert + TLS 1.2+ policy · rds.force_ssl = 1 · aws:SecureTransport deny · TLS-only security-group ports + Flow Logs
  • You saw what a disabled key does. What breaks the day someone schedules deletion of a customer managed key that's actively in use — and how would you catch it in the 7-day window?
