Module 5 — Security IN the Cloud · Part 3

🎯 Objective

Work three realistic incidents through a cloud-native IR workflow — detect, analyze, contain, eradicate, recover, learn — and perform the real containment actions in the class account.

  • Investigate GuardDuty sample findings (Resource / Actor / Action)
  • Contain a stolen role session: Revoke active sessions + a quarantine security group
  • Contain a compromised IAM user: deactivate the key, deny everything, trace it in CloudTrail
  • Read the policy AWS attaches to leaked keys — and find what it does not block

👥 Shared class account: everyone works in the same AWS account. Start every resource name with your student ID, and only open, change, or delete resources that start with your ID.

📚 Terms You'll See

  • GuardDuty — AWS threat-detection service; analyzes CloudTrail, VPC Flow Logs and DNS logs
  • finding — a detection, scored Low / Medium / High (and Critical)
  • Sample finding — a GuardDuty-generated example, titled [SAMPLE], with placeholder values
  • Detective — service that builds investigation graphs from CloudTrail, VPC Flow Logs & GuardDuty
  • Break-glass role — pre-provisioned emergency IAM role with elevated access
  • Forensic account — isolated AWS account for evidence & analysis
  • IMDS — EC2 Instance Metadata Service; classic SSRF target for stealing role credentials
  • aws:TokenIssueTime — IAM condition key: when a temporary credential was issued
  • Quarantine SG — security group with no inbound and no outbound rules
  • SSM Automation runbook — Systems Manager document you can run by hand or from EventBridge

⛔ Step 4 — Revoke the Stolen Sessions

Removing a role from an instance profile does not invalidate credentials already issued — they stay valid until they expire (up to hours).

  1. Open <student-id>-prod-api-role → the Revoke sessions tab
  2. Choose Revoke active sessions
  3. Tick the acknowledgement box → choose Revoke active sessions
  4. Open the Permissions tab → expand the new inline policy
✅ Check: a new inline policy named AWSRevokeOlderSessions: Effect: Deny, Action: *, Resource: *, Condition: DateLessThan aws:TokenIssueTime = <about 30 seconds after you clicked> (the extra 30 s covers policy propagation).

🧪 What That Policy Actually Did

  • Any credential issued before the timestamp → every call is denied, explicitly
  • Credentials issued after it → work normally, so the real instance recovers when it fetches fresh credentials from IMDS
  • Verified in a test account: a session issued before the revoke got
    AccessDenied … not authorized to perform: s3:ListAllMyBuckets with an explicit deny in an identity-based policy
  • A session issued ~10 s after the click was still denied (inside the 30 s buffer); one issued ~45 s after listed buckets normally
  • Catch: if the SSRF hole is still open, the attacker can steal the new credentials too — revoke buys time; the quarantine and fix close the door

🧱 Step 5 — Build a Quarantine Security Group

The class account has no default VPC, so create your own empty one (no subnets, no cost).

  1. VPC → Your VPCs → Create VPC → Resources to create: VPC only
  2. Name tag: <student-id>-lab6; IPv4 CIDR: 10.60.0.0/16 → Create VPC
  3. Security groups (left menu) → Create security group
  4. Name <student-id>-quarantine; description IR quarantine - no inbound or outbound; VPC <student-id>-lab6
  5. Inbound rules: add none. Outbound rules: if the form shows the default All traffic · 0.0.0.0/0 rule, choose Delete on it
  6. Create security group; if the Outbound rules tab still lists a rule → Edit outbound rules → Delete → Save rules
✅ Check: the group's Inbound rules and Outbound rules tabs both show no rules. A new SG normally gets an allow-all outbound rule — removing it is what makes this a quarantine SG.

📖 Scenario A — Sample Playbook

  1. Preserve: snapshot the instance's EBS volume(s) (ec2:CreateSnapshot); export CloudTrail & VPC Flow Logs; tag the instance as evidence
  2. Contain: Revoke active sessions on the role (what you just did — AWSRevokeOlderSessions)
  3. Contain: swap the instance's SGs for the quarantine SG. SG changes block new flows, but already-tracked connections can continue — add a deny-all NACL on the subnet to cut existing sessions. Runbook: AWSSupport-ContainEC2Instance
  4. Analyze: pivot in Detective from the finding to the role's API activity — what else did 203.0.113.42 touch?
  5. Eradicate: terminate, redeploy from a known-good AMI/IaC, require IMDSv2 (hop limit 1), trim the role's permissions

Root cause is typically: SSRF in the app, an over-permissive instance profile, or IMDSv1 still enabled.

Tested with the CLI: the key worked before; seconds after deactivation every call returned InvalidClientTokenId — The security token included in the request is invalid.

🕵️ Step 9 — Trace It in CloudTrail

  1. CloudTrail → Event history
  2. Lookup attribute Resource name = <student-id>-jdoe
  3. Open the UpdateAccessKey event → view the event record JSON
  4. Find userIdentity, sourceIPAddress, userAgent, requestParameters.status
  5. Change the attribute to AWS access key = jdoe's key ID — what did the key itself do?
✅ Check: CreateUser, CreateAccessKey, UpdateAccessKey, AttachUserPolicy — all with User name = you. Delivery delay: in testing, events appeared in Event history about 2 minutes after the action (typically within ~5 minutes, not guaranteed). Nothing showing yet? Wait and refresh. The access-key search is empty — the key was never used.

📖 Scenario B — Sample Playbook

  1. Deactivate all of jdoe's access keys (iam:UpdateAccessKey) — effective within seconds. Delete them (iam:DeleteAccessKey) once evidence is captured
  2. Attach AWSDenyAll (explicit deny beats every allow) and delete the console password (login profile) if there is one
  3. Preserve: query CloudTrail (Event history — 90 days of management events — or CloudTrail Lake) for everything jdoe did; export it
  4. Scope the data: GetObject is an S3 data event — it is not in Event history. You need S3 data events or server access logs enabled before the incident
  5. Notify: incident commander → legal → privacy/DPO → customer comms if exfiltration is confirmed
  6. Long-term: move humans to IAM Identity Center (short-lived creds); Config rule iam-user-unused-credentials-check; EventBridge → Lambda/SSM auto-response on this finding type

A CI pipeline's long-lived key was committed to a public repo. AWS detected it and applied a quarantine policy — but that policy only blocks a list of actions.

🛠️ Step 10 — Read the Quarantine Policy

  1. IAM → IAM users → <student-id>-jdoe → Permissions → Add permissions → Add permissions
  2. Attach policies directly → search AWSCompromisedKeyQuarantineV3 → tick → Next → Add permissions
  3. Click the policy name → Permissions tab → JSON
  4. Skim the Action list. Is sts:AssumeRole there? secretsmanager:GetSecretValue? ec2:TerminateInstances?
✅ Check: the user now has two AWS managed policies. The JSON has two Deny statements: a list of about 100 actions (98 at time of writing) and a second denying kms:CreateGrant unless called via an AWS service. None of the three actions named in item 4 above is on the list. AWS revises this list — read the live JSON, not a blog post.

📖 Scenario C — Sample Playbook (1/2)

  • What the quarantine blocks: cost/fraud and persistence actions — ec2:RunInstances, Lightsail, Bedrock InvokeModel, iam:CreateUser / CreateAccessKey / Attach*Policy / CreateRole, sts:GetSessionToken, plus some reads (s3:GetObject, s3:ListBucket, iam:ListUsers, cloudtrail:LookupEvents)
  • Why it isn't enough: it is a deny list. Everything else the user is allowed stays allowed — sts:AssumeRole into other roles, secretsmanager:GetSecretValue, ssm:GetParameter, DynamoDB reads, ec2:TerminateInstances, RDS deletes…
  • And it came late: anything done in the 47 minutes before it was attached (new users, keys, roles) is already in place
  • Contain: deactivate the key (iam:UpdateAccessKey → Inactive) using your credentials; attach AWSDenyAll; delete the key after the evidence export

📖 Scenario C — Sample Playbook (2/2)

  • Analyze: CloudTrail Event history filtered by AWS access key = the exposed key (exactly what you did in Step 9). Worry most about CreateUser, CreateAccessKey, CreateLoginProfile, AttachUserPolicy, CreateRole / UpdateAssumeRolePolicy (persistence), AssumeRole (lateral movement), RunInstances in unused regions (crypto-mining), GetSecretValue (data theft)
  • Eradicate: delete anything the attacker created; check every region — Event history is per-region
  • Recover: move the pipeline to an IAM role assumed via OIDC (GitHub Actions → sts:AssumeRoleWithWebIdentity) — short-lived creds, no stored key
  • Prevent: secret scanning / push protection in the repo, pre-commit hooks, a Config rule or Access Analyzer review that flags IAM users with keys; scrub the commit from history (the key is burned either way)

📘 Step 11 — Built-in IR Runbooks

  1. Systems Manager → Documents (under Change Management Tools / Shared Resources)

Leave GuardDuty alone. It is shared by the whole class — disabling it would delete everyone's findings.
