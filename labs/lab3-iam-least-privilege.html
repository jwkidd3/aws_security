Lab 3

IAM Least Privilege Review

Module 3 — Security IN the Cloud · Part 1

🎯 Objective

Build an over-permissive application role in the class account, prove how dangerous it is with the IAM Policy Simulator, then replace its policy with a least-privilege version and prove the app can still do its job — and nothing else. Finally, review an S3 bucket policy for the same workload.

Least privilege = grant only the permissions actually needed. Everything in this lab is done in the AWS web console.

👥 Shared class account: everyone works in the same AWS account. Start every resource name with your student ID, and only open, change, or delete resources that start with your ID.

📚 Terms You'll See

  • IAM policy — JSON document listing allowed/denied actions on resources; a customer managed policy is one you create and can attach to many identities
  • IAM role — identity a workload assumes (no long-lived credentials)
  • ARN — globally-unique ID for an AWS resource, e.g., arn:aws:s3:::my-bucket
  • IAM Policy Simulator — console tool that evaluates a policy against API actions and shows allowed/denied
  • Implicit deny — no statement allows the action · Explicit deny — a Deny statement matched (always wins)
  • Policy validation — IAM Access Analyzer checks run as you edit a policy (security warnings, errors, suggestions)
  • S3 Block Public Access — bucket/account switches that reject public bucket policies and ACLs
  • SQS — message queue · DynamoDB — NoSQL table · CloudWatch Logs — log groups and streams
  • PassRole — permission to hand a role to a service (a classic privilege-escalation hole when broad)

📋 Scenario — <student-id>-app-orders-processor

You're reviewing the IAM role attached to an app that processes customer orders. It runs on EC2 in the class account, region us-east-1, and needs only to:

  • Read order events from one SQS queue: <student-id>-orders-incoming
  • Write to one DynamoDB table: <student-id>-orders
  • Write logs to its own CloudWatch log group: <student-id>-orders-app-logs

You won't create the queue, table, or log group — the Policy Simulator only needs their ARNs. Find your 12-digit account ID in the account menu (top right of the console) and note it; you'll paste it into ARNs throughout the lab.

📜 The Current Policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AppAccess",
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    },
    {
      "Sid": "ExtraStuff",
      "Effect": "Allow",
      "Action": [
        "s3:*", "iam:PassRole",
        "dynamodb:*", "sqs:*", "logs:*"
      ],
      "Resource": "*"
    }
  ]
}

"*" in Action means "every possible action." "*" in Resource means "every resource ARN" — any region, and other accounts' resources too wherever their resource policies allow it.

✏️ Task 1 — Spot the Violations (3 min)

Before touching the console, list at least 4 violations in the current policy. Consider:

  • Action wildcards and resource wildcards
  • Privileges the workload doesn't need at all
  • Privilege-escalation risks (like iam:PassRole)
  • Cross-region or cross-account exposure
  • Redundant or misleading statements

Keep your list — you'll check it against what the policy validator and the Policy Simulator show you next.

🛠️ Step 1 — Create the Broad Policy

  1. Sign in to the class AWS account and set the region selector to US East (N. Virginia) us-east-1
  2. Open IAM → Policies → Create policy
  3. In the Policy editor, switch from Visual to JSON
  4. Delete the starter text and paste the Current Policy from the previous slide
  5. Look at the policy-validation panel below the editor (Security, Errors, Warnings, Suggestions) and read each finding
  6. Choose Next, name it <student-id>-orders-broad, then Create policy

✅ Check: the validator reports 2 security warnings and 1 warning, and the policy still saves — validation warns, it doesn't block.

🛠️ Step 2 — Create the App Role

  1. IAM → Roles → Create role
  2. Trusted entity type: AWS service · Service or use case: EC2 · use case EC2 → Next
  3. Search for <student-id>-orders-broad, tick it → Next
  4. Role name: <student-id>-app-orders-processor → Create role
  5. Open the new role and confirm the Permissions tab lists <student-id>-orders-broad

✅ Check: the role's Trust relationships tab shows "Service": "ec2.amazonaws.com" — only EC2 can assume this role. Nobody runs an instance with it in this lab; the Policy Simulator evaluates it directly.

🛠️ Step 3 — Prove the Damage in the Policy Simulator

  1. IAM → navigation pane → Policy simulator (keep Principal mode; the legacy simulator at policysim.aws.amazon.com is being retired)
  2. Under Identities choose Add identity → filter by entity type Role → tick <student-id>-app-orders-processor → Add identities; Identity-based policies lists <student-id>-orders-broad
  3. Add actions: IAM → CreateUser, PassRole · S3 → DeleteBucket · EC2 → RunInstances
  4. Leave every Resource as * → Simulate

✅ Check: every row shows Allowed (RunInstances expands into 5 resource rows) with Explicit allow in <student-id>-orders-broad — 2 statements for PassRole and DeleteBucket, which both statements cover. An order processor that can create IAM users, pass any role, delete buckets, and launch instances is one stolen credential away from a full account takeover.

✅ Task 1 — Sample Answer

  • "Action": "*" + "Resource": "*" is full administrator access — the app needs about nine actions
  • iam:PassRole on "*" lets the app hand any role (including admin roles) to a new EC2 instance or Lambda function — privilege escalation
  • IAM write actions (CreateUser, AttachRolePolicy…) let an attacker create persistent backdoor identities
  • s3:*, dynamodb:*, sqs:*, logs:* include destructive actions (DeleteBucket, DeleteTable, PurgeQueue, DeleteLogGroup) on every resource
  • No region restriction — stolen credentials can build resources in any region, where nobody is looking
  • "Resource": "*" also reaches other accounts' buckets and queues wherever their resource policies are loose
  • ExtraStuff is redundant with AppAccess, which hides intent and makes review harder

✏️ Task 2 — Write the Least-Privilege Policy

Take 2 minutes: for each requirement, jot down the action names and the resource ARN you'd use, then compare your notes with the sample on the next slide.

  • DynamoDB: GetItem, PutItem, UpdateItem, BatchWriteItem on table <student-id>-orders
  • SQS: ReceiveMessage, DeleteMessage, GetQueueAttributes on queue <student-id>-orders-incoming
  • CloudWatch Logs: CreateLogStream, PutLogEvents on log group <student-id>-orders-app-logs (append :* to cover its log streams)
  • Every ARN uses the class account ID and us-east-1
  • Bonus: add Deny statements that block other regions (aws:RequestedRegion) and non-TLS requests (aws:SecureTransport)

✅ Task 2 — Sample Solution

Replace ACCOUNT-ID (3 places) and STUDENT-ID (3 places) before you paste it.

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ReadOrderQueue", "Effect": "Allow",
      "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage", "sqs:GetQueueAttributes"],
      "Resource": "arn:aws:sqs:us-east-1:ACCOUNT-ID:STUDENT-ID-orders-incoming" },
    { "Sid": "WriteOrdersTable", "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:UpdateItem", "dynamodb:BatchWriteItem"],
      "Resource": "arn:aws:dynamodb:us-east-1:ACCOUNT-ID:table/STUDENT-ID-orders" },
    { "Sid": "WriteAppLogs", "Effect": "Allow",
      "Action": ["logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "arn:aws:logs:us-east-1:ACCOUNT-ID:log-group:STUDENT-ID-orders-app-logs:*" },
    { "Sid": "DenyOutsideUsEast1", "Effect": "Deny", "Action": "*", "Resource": "*",
      "Condition": { "StringNotEquals": { "aws:RequestedRegion": "us-east-1" } } },
    { "Sid": "DenyNonTLS", "Effect": "Deny", "Action": "*", "Resource": "*",
      "Condition": { "Bool": { "aws:SecureTransport": "false" } } }
  ]
}

🛠️ Step 4 — Create the Least-Privilege Policy

  1. IAM → Policies → Create policy → JSON
  2. Paste the sample solution (or your own version) with your account ID and student ID filled in
  3. Read the policy-validation panel
  4. Next → name it <student-id>-orders-least → Create policy

✅ Check: the validator shows 0 security warnings, errors, warnings, and suggestions. If you see a finding, compare your JSON to the sample — a typo in an ARN or action name is the usual cause.

🛠️ Step 5 — Swap the Policy on the Role

  1. IAM → Roles → <student-id>-app-orders-processor → Permissions tab
  2. Tick <student-id>-orders-broad → Remove → confirm Remove
  3. Add permissions → Attach policies
  4. Search for <student-id>-orders-least, tick it → Add permissions

✅ Check: the Permissions policies list shows only <student-id>-orders-least. Removing a policy from a role does not delete the policy — <student-id>-orders-broad still exists under Policies.

🛠️ Step 6 — Re-Simulate the App's Actions

  1. Refresh the Policy simulator and reselect your role so Identity-based policies shows <student-id>-orders-least; choose Remove all to clear the old actions
  2. Expand Global request conditions and set aws:RequestedRegion = us-east-1 (leave aws:SecureTransport blank)
  3. Add actions: SQS → ReceiveMessage, SendMessage · DynamoDB → PutItem, DeleteTable · CloudWatch Logs → PutLogEvents, DeleteLogGroup
  4. Edit each row's Resource (pencil icon) → Simulate:
    SQS: arn:aws:sqs:us-east-1:ACCOUNT-ID:STUDENT-ID-orders-incoming
    DynamoDB: arn:aws:dynamodb:us-east-1:ACCOUNT-ID:table/STUDENT-ID-orders
    Logs: arn:aws:logs:us-east-1:ACCOUNT-ID:log-group:STUDENT-ID-orders-app-logs:log-stream:i-0abc123

Resource left as *? Then even the allowed actions show denied. The policy only allows specific ARNs, so the simulator needs one to match.

🛠️ Step 7 — Prove the Denies

  1. Remove all. Keep aws:RequestedRegion = us-east-1. Add and simulate IAM CreateUser + PassRole, S3 DeleteBucket, and EC2 RunInstances (resource *)
  2. Change aws:RequestedRegion to us-east-2. Add SQS ReceiveMessage on your queue ARN → Simulate

✅ Check: (1) all four are Denied — Implicit deny due to no statement(s) matching. (2) ReceiveMessage is denied by DenyOutsideUsEast1 even though the allow statement matches — explicit deny wins. The four rows from (1) now also show an explicit deny from DenyOutsideUsEast1.

📎 Task 3 — Review a Bucket Policy

The app now needs to read invoice PDFs from an S3 bucket. A developer wrote this bucket policy. Account 444455556666 is a billing partner that uploads invoices; nobody else should have access. Take 2 minutes and list at least three problems.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AppRead",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::BUCKET-NAME",
                   "arn:aws:s3:::BUCKET-NAME/*"]
    },
    {
      "Sid": "PartnerUpload",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::444455556666:root" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::BUCKET-NAME/*"
    }
  ]
}

✅ Task 3 — Sample Answer

  • "Principal": "*" with s3:* makes the bucket readable, writable, and deletable by anyone on the internet. S3 Block Public Access (on by default for new buckets) rejects a public policy like this
  • s3:* includes s3:PutBucketPolicy and s3:DeleteBucketPolicy — anyone could rewrite or remove the policy itself
  • The app only needs s3:GetObject, and only for objects — not bucket-level actions
  • The partner statement trusts the whole partner account. Scope it to the partner's upload role and an invoices/ prefix
  • No TLS requirement — requests over plain HTTP aren't denied
  • Principals must be real: a typo'd or deleted role ARN makes the whole policy unsaveable
