👤 IAM — Authn, Authz & Building Blocks

Authentication = who are you? · Authorization = what can you do? IAM handles both; most policy work is authz.

  • User — a long-lived identity for a human or legacy app (avoid where possible)
  • Group — a container of users; attach policies to groups, not users
  • Role — an identity that workloads or federated humans assume temporarily (short-lived creds)
  • Policy — a JSON document granting or denying actions on resources
  • Principal — who/what is making the request (user, role, service)

🪪 Identity Federation & IAM Identity Center

  • IAM Identity Center (formerly AWS SSO) — central sign-on across all AWS accounts
  • Federate from your corporate IdP (Okta, Entra ID, Ping, Google Workspace) with SAML or OIDC
  • Humans log in once → assume short-lived roles in each account — no per-account IAM users
  • Machine workloads use IAM roles (EC2 instance profiles, ECS task roles, Lambda execution roles)
  • Goal: no long-lived access keys anywhere you can avoid them

🗝️ Root Account & MFA

  • The root user is the original all-powerful account — lock it away
  • MFA required on root — prefer a hardware key (FIDO2)
  • Remove all root access keys; use root only for billing and rare recovery tasks
  • Every human account must have MFA — no exceptions
  • Do daily work through IAM Identity Center or IAM roles, never as root

📜 Anatomy of an IAM Policy

{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::reports-prod/*",
  "Condition": {
    "StringEquals": { "aws:RequestedRegion": "us-east-1" },
    "Bool":         { "aws:MultiFactorAuthPresent": "true" }
  }
}
  • Effect — Allow or Deny (explicit Deny always wins)
  • Action — API call(s), e.g., s3:GetObject
  • Resource — ARN(s) the actions apply to
  • Condition — constraints: region, source IP, MFA, tag values…

🎯 Least Privilege & Policy Tooling

  • Least privilege — grant only the actions actually used, on the specific resources needed
  • Avoid "Action": "*" and "Resource": "*" in anything that runs in production
  • IAM Access Analyzer — flags policies that grant access outside your account or org; can generate a policy from observed CloudTrail activity
  • IAM Policy Simulator — test a proposed policy against real API calls before deploying
  • Last Accessed Info in the IAM console — see which services a role actually used (and prune)

📎 Resource-Based Policies

Policies attached to the resource rather than the principal — cross-account access without assumed roles.

  • S3 bucket policies — who can read/write objects in this bucket
  • KMS key policies — who can use this key (required, not optional)
  • SQS / SNS / Lambda resource policies — allow other accounts or services to invoke
  • Same account: either the identity policy or the resource policy can allow. Cross-account: both must allow. An explicit Deny always wins

⚖️ How IAM Decides — and How to Test It

  • Implicit deny by default → an Allow grants → an explicit Deny overrides everything
  • A role has two policies: a trust policy (who may assume it, e.g., ec2.amazonaws.com) and permissions policies (what it can do)
  • AWS managed policies are written by AWS; customer managed policies are yours to scope
  • iam:PassRole lets a principal hand a role to a service — broad PassRole = privilege escalation
  • Test before you deploy: the IAM policy editor's Access Analyzer validation, and the IAM Policy simulator

🪣 S3 Access Guardrails

  • S3 Block Public Access — on by default for new buckets; S3 rejects a bucket policy that would make the bucket public
  • Bucket-policy principals must exist — S3 rejects unknown accounts or roles ("Invalid principal")
  • Deny any request where aws:SecureTransport is false → TLS-only bucket
  • AWS CloudShell — a browser terminal (console icon, top bar) with the AWS CLI, signed in as you; labs use it to send test requests

🛡️ Data Protection — The Big Picture

  • Classify first — Public, Internal, Confidential, Restricted — controls follow the class. Amazon Macie scans S3 to find sensitive data (PII, PHI, credentials) you didn't know you had
  • Encrypt at rest — most AWS services encrypt by default; you choose which key — and can enforce it with bucket policies that deny uploads using the wrong key
  • Encrypt in transit — TLS everywhere, including between services inside your VPC
  • Limit direct access — pull data through APIs, not through human console sessions
  • Protect backups — encrypted, versioned, tested, and often in a separate account

🔐 KMS — Key Management Service

  • KMS key — the logical key you grant usage of via key policies (AWS used to call these "customer master keys," or CMKs)
  • AWS managed key — AWS creates and controls (e.g., aws/s3); simple, no monthly fee, can't be shared across accounts
  • Customer managed key — you own the key policy, rotation, grants, audit
  • CloudHSM-backed key — a KMS key whose material lives in a dedicated hardware security module (HSM) cluster you own, rather than in shared KMS infrastructure — reach for it only when regulation (e.g., certain finance or gov workloads) requires single-tenant key hardware
  • Envelope encryption — KMS encrypts a per-object data key; the data key encrypts the data. Efficient at scale.
  • Every use of a KMS key is logged in CloudTrail

🔒 Encryption in Transit & Secrets

  • TLS on every endpoint — AWS APIs support TLS 1.2+, but some endpoints (e.g., S3) still accept plain HTTP — enforce TLS with aws:SecureTransport
  • ACM — free public certs with auto-renewal for ELB, CloudFront, API Gateway
  • Enforce in-transit encryption on databases too (rds.force_ssl on RDS, TLS on Redis) and on S3 (deny requests where aws:SecureTransport is false)
  • Secrets Manager — store & auto-rotate secrets; workloads fetch via IAM role at runtime
  • Never commit credentials to code, env files, or AMIs

🧰 S3, KMS & RDS in Practice

  • S3 encryption types: SSE-S3 (S3-managed keys) · SSE-KMS (a KMS key you choose) · DSSE-KMS (dual-layer)
  • S3 Bucket Keys — a bucket-level data key that cuts KMS requests and cost for SSE-KMS
  • Policy condition operators: StringNotEquals, …IfExists (also matches when the key is absent), Null (is the key present?); kms:ViaService limits a key to one service
  • Disable a KMS key → decrypts fail immediately; delete requires a 7–30 day waiting period
  • RDS parameter groups hold engine settings: PostgreSQL rds.force_ssl (default 1 on 15+) and ssl_min_protocol_version; MySQL require_secure_transport
